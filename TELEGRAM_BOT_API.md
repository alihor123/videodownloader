# API для Telegram-бота

## Идея

Сейчас backend больше рассчитан на браузер:

1. Фронт создаёт задачу скачивания.
2. Backend готовит файл или прямой поток.
3. Фронт ждёт `ready`.
4. Фронт открывает `download_url`.
5. Backend отдаёт файл пользователю.

Для Telegram-бота нужен похожий сценарий, но финальный шаг другой:

1. Бот создаёт задачу скачивания.
2. Backend скачивает файл на сервер в `tmp`.
3. Бот получает данные о готовом файле.
4. Бот отправляет файл в Telegram.
5. Если файл не подходит под лимиты Telegram или не открылся с диска, бот отправляет пользователю ссылку.

Главное условие: бот должен быть запущен на том же сервере, что и backend. Тогда `file_path` будет полезен, потому что бот сможет открыть файл напрямую с локального диска.

## Почему не надо стримить напрямую в Telegram

Идея "скачивать с YouTube и сразу потоком заливать в Telegram API" выглядит красиво, но на практике это слишком сложный путь для текущего этапа.

Проблемы прямого стрима:

- Telegram Bot API обычно принимает файл как `multipart/form-data`;
- библиотекам часто нужны имя файла, размер и file-like object;
- сложнее заранее проверить размер и лимиты;
- при обрыве потока сложно понять, где именно умерло: YouTube, backend, bot или Telegram;
- retry становится больнее, потому что файл не сохранён локально;
- прогресс, диагностика и повторная отправка становятся менее прозрачными.

Даже если стримить напрямую, байты всё равно должны пройти через твой сервер в Telegram. Магического пути "YouTube сразу пользователю в Telegram" здесь нет.

Более надёжная схема:

```text
YouTube -> backend сохраняет файл в tmp -> bot открывает file_path -> Telegram API -> пользователь
```

Это не оверинжиниринг. Это нормальная простая схема с понятной точкой контроля.

## Почему нужен режим без stream

В текущей логике есть `fast`-режим. Он может не скачивать файл на сервер, а получить прямую ссылку на поток YouTube и стримить её через backend.

Для бота это неудобно:

- локального файла может не быть;
- `file_path` будет пустым;
- бот не сможет отправить файл через `send_document` или `send_video` с диска;
- прямые YouTube-ссылки могут протухать;
- fallback и повторная отправка становятся менее предсказуемыми.

Поэтому для бота нужен режим, который явно говорит backend: файл надо сохранить на сервере.

Пример request body:

```json
{
  "url": "https://www.youtube.com/watch?v=...",
  "format": {
    "height": 720,
    "fast": false
  },
  "stream": false
}
```

Смысл `stream=false`: не пытаться работать через fast/direct stream, а всегда готовить локальный файл.

## Поведение режимов

### `stream=true`

Это браузерный сценарий.

- Можно пробовать `fast`.
- Можно отдавать прямой поток через backend.
- Если fast не сработал, можно fallback на file download.
- Пользователь получает файл через `download_url`.

### `stream=false`

Это сценарий для Telegram-бота.

- Fast/direct stream не пробуется.
- Backend всегда скачивает файл на сервер.
- После `ready` бот получает данные о файле.
- Бот открывает `file_path` и отправляет файл в Telegram.
- Если локальная отправка невозможна, бот отправляет `download_url`.

## Что добавить в API

В `CreateDownloadTaskRequest`:

```python
stream: bool = True
```

В `DownloadTask`:

```python
stream: bool = True
```

В `create_download_task(...)` нужно сохранить этот параметр в задаче.

## Что изменить в запуске задачи

Сейчас логика примерно такая:

```python
if task.requested_fast:
    fast_ready = await prepare_fast_download(task_id)
    if fast_ready:
        return

await prepare_file_download(task_id)
```

Для bot-сценария нужно учитывать `stream`:

```python
if task.stream and task.requested_fast:
    fast_ready = await prepare_fast_download(task_id)
    if fast_ready:
        return

await prepare_file_download(task_id)
```

Так `fast` будет пробоваться только для браузерного режима.

## Какие данные вернуть боту

Когда задача готова и `stream=false`, боту полезен ответ такого вида:

```json
{
  "task_id": "...",
  "status": "ready",
  "download_url": "/api/youtube/download-tasks/.../download",
  "file_path": "/root/videodownloader/back/tmp/...",
  "filename": "video.mp4",
  "safe_title": "video",
  "file_ext": "mp4",
  "media_type": "video/mp4",
  "size_bytes": 12345678
}
```

`file_path` нужен только внутреннему коду бота. Пользователю его показывать не нужно.

`download_url` нужен как запасной вариант, если:

- файл слишком большой для Telegram;
- Telegram API отказался принимать файл;
- бот не смог открыть файл по `file_path`;
- нужно отправить пользователю обычную ссылку.

## Лимиты Telegram

У Telegram Bot API есть ограничения на размер файлов. Поэтому боту нужно проверять размер перед отправкой.

Желательная логика:

1. Получить `file_path` и `size_bytes`.
2. Если размер подходит, отправить файл через Telegram API.
3. Если размер не подходит, отправить `download_url`.
4. После успешной отправки файла удалить локальный файл.

Свой Telegram Bot API server имеет смысл рассматривать только если обычные лимиты реально мешают. На старте лучше не усложнять систему.

## Удаление файлов

Для браузера файл можно удалять после завершения HTTP-ответа.

Для бота лучше другой жизненный цикл:

1. Backend скачал файл.
2. Бот получил `file_path`.
3. Бот отправил файл в Telegram.
4. Бот подтвердил успех.
5. Файл удаляется.

Если удалить файл сразу после подготовки, бот может не успеть его открыть.

Если удалить файл после `/download`, это не поможет bot-сценарию, потому что бот может вообще не использовать `/download`, а читать файл напрямую с диска.

Поэтому для бота нужен отдельный контроль очистки:

- либо бот сам вызывает `remove` после успешной отправки;
- либо backend даёт endpoint для удаления задачи/файла;
- TTL-cleanup остаётся страховкой от забытых файлов.

## Нужный endpoint

Хороший вариант: добавить отдельный endpoint для данных файла без скачивания:

```text
GET /api/youtube/download-tasks/{task_id}/file
```

Он возвращает JSON:

```json
{
  "task_id": "...",
  "status": "ready",
  "file_path": "...",
  "download_url": "...",
  "filename": "...",
  "media_type": "...",
  "size_bytes": 12345678
}
```

Так `/download` остаётся браузерным endpoint, а бот получает отдельный понятный контракт.

## Минимальный план изменений

1. Добавить `stream` в request body.
2. Сохранить `stream` в `DownloadTask`.
3. Не пробовать fast, если `stream=false`.
4. Расширить response или добавить `/file` endpoint.
5. Вернуть `file_path`, `filename`, `media_type`, `size_bytes`, `download_url`.
6. Реализовать удаление файла после успешной отправки ботом.
7. Оставить TTL-cleanup как запасную защиту.

## Итоговая рекомендация

Начинать нужно не с прямого стрима в Telegram, а с локального файла:

```text
backend tmp -> bot reads file_path -> Telegram API
```

Это проще, надёжнее и сильно легче отлаживать. Прямой стрим в Telegram можно оставить как далёкую оптимизацию, если позже появится реальная причина экономить диск или время записи файла.
